# Ревью зависаний терминалов — 11 сентября 2026

Проверены цепочки клавиатура → IPC → TerminalManager → Rust sidecar → PTY, обратный поток вывода и отправка через `orc tell`.

Наиболее конкретная воспроизведённая причина длительных зависаний: при заполнении Rust-истории до 1 000 000 байт обрезка могла попасть внутрь многобайтового символа. Тест с историей из букв «я» и добавлением одного ASCII-символа упал с `start byte index 1 is not a char boundary`. Поток чтения завершался паникой до уведомления об окончании сессии. Оболочка при этом могла оставаться запущенной, а интерфейс — показывать живой терминал. После исправления тот же тест проходит.

Связанная архитектурная проблема: обработка команд зависела от пропускной способности вывода. Rust держал общий mutex во время блокирующего `stdout.write_all/flush`. Если Electron переставал достаточно быстро читать вывод, командный цикл тоже останавливался. Вынос только JSON-сериализации за mutex эту зависимость не устранял.

## Исправления этого ревью

| Дефект | Исправление | Файл |
| --- | --- | --- |
| **Критический:** паника при обрезке Unicode-истории | Граница обрезки выравнивается по UTF-8; неполные символы сохраняются между чтениями, а не заменяются ошибочными символами | `native/orcspace-app/src/engine.rs` |
| Переполненный stdout блокировал командный цикл | stdout принадлежит отдельному потоку; ответы передаются через ограниченную неблокирующую очередь и получают приоритет между порциями вывода | `native/orcspace-app/src/main.rs` |
| Ctrl+C ожидал обычный ввод и отклонялся после тайм-аута ACK | Прерывание обходит очередь ввода и блокировку повторных записей; отменяет старые ожидающие сообщения и отложенный Enter | `src/main/terminals.ts`, `src/main/rustPtySidecar.ts` |
| Потерянный ACK мог навсегда заблокировать ввод | После короткого периода отклонения накопленных запросов новая запись может повторно проверить доступность движка | `src/main/rustPtySidecar.ts` |
| Ограничитель stdout удалял готовые ACK/exit вместе с большим пакетом | Полные события разбираются до ограничения размера незавершённого пакета | `src/main/rustPtySidecar.ts` |
| По истечении ожидания очередь запускала ввод параллельно старой операции | Просроченная операция получает ошибку и не отправляет байты | `src/main/terminals.ts` |
| `orc tell` падал с `imagePaths is not defined` даже без картинки | Используется существующий разбор аргументов; интеграционный тест отправки проходит | `cli/orc.mjs` |
| Поздние data/exit старой сессии могли затронуть новую | У каждой нативной сессии свой внутренний ID; события старой сессии отбрасываются, её ресурсы освобождаются | `src/main/rustPtySidecar.ts` |
| Ошибка движка могла сопровождаться ложным успешным перезапуском | Неисправный backend больше не принимает spawn/write; ожидающие записи завершаются ошибкой | `src/main/rustPtySidecar.ts` |
| Завершение sidecar сразу убивало движок, не давая ему обработать shutdown | Сначала отправляется shutdown и закрывается stdin, принудительное завершение — через 5 секунд при необходимости | `src/main/rustPtySidecar.ts` |
| Падение движка могло оставлять дочерние процессы | Windows Job Object ограничивает срок жизни дерева процессов сроком жизни движка | `native/orcspace-app/src/process_job.rs` |
| Вывод накапливался перед/внутри парсера xterm | Не более 256K UTF-16 единиц в очереди и одной порции 32K внутри парсера; при перегрузке сохраняется свежий хвост | `terminalRenderQueue.ts`, `TerminalWidget.tsx` |
| Поздний callback восстановления мог продолжить старую историю после тайм-аута | Завершение восстановления инвалидирует его поколение | `TerminalWidget.tsx` |
| Общая куча интерфейса была ограничена 384 МБ независимо от числа терминалов | Убран искусственный лимит, используется выбор V8; убран обход GPU blocklist | `src/main/bootstrap.ts` |
| После падения renderer оставался недоступный интерфейс | Автоперезагрузка интерфейса с подключением к прежним PTY, максимум две попытки в минуту; затем видимое сообщение об ошибке | `src/main/windowManager.ts` |
| Входная очередь Rust была неограниченной; аварийная очистка могла закрывать ConPTY до остановки процессов | Очередь ограничена 1024 командами; остановка дерева предшествует закрытию master | `main.rs`, `engine.rs` |

В рабочем дереве до начала ревью уже были изменения PTY: отдельные потоки записи и управления, распознавание зависшей записи и аварийное прерывание. Они сохранены. Перечисленные выше дефекты оставались поверх этих изменений.

## Проверка

- `npm test`: 442/442.
- Rust: `node scripts/native-cargo.mjs test --bin orcspace --manifest-path native/orcspace-app/Cargo.toml`: 19/19.
- `npm run typecheck`: успешно.
- Release-сборка Rust и `npm run build`: успешно.
- `git diff --check`: успешно.

Новые регрессии проверяют потерю ACK, восстановление ввода, Ctrl+C при незавершённой записи, отмену старого текста/Enter, просроченную очередь, сохранение ACK/exit при большом выводе и обработку команд при отсутствии потребителя ответов. Тесты sidecar также обращаются к собранному Rust-движку.

Нагрузочные проверки `src/main/terminalStress.test.ts` запускают реальные изолированные процессы, без внешних AI-агентов:

- Три одновременно печатающих Unicode-терминала и четвёртый терминал для проверки ввода: около 7,84 МБ вывода, без повреждения UTF-8. В отдельных прогонах максимальная задержка ACK составила 3,0–3,1 мс; это измерение локального теста, не гарантия задержки на любой машине.
- Восемь последовательных замен сессии с тем же видимым ID: последняя принимает команду.
- Нормальное закрытие и принудительное падение движка: тестовый дочерний процесс прекращает работу.
- Чтение stdout движка принудительно приостановлено во время непрерывного вывода: dispose всё равно останавливает целевой процесс; после возобновления чтения движок запускает новую сессию.

Проверки Electron UI прошли: создание/ввод/закрытие терминала, изменение размеров трёх Code-терминалов, вставка только в сфокусированный из четырёх терминалов. Отдельный `terminal-recovery.spec.ts` принудительно роняет renderer, дожидается восстановления и выполняет команду с переменной, установленной в оболочке до падения: это подтверждает сохранение самой оболочки, а не подмену новой сессией.

Windows-механизм завершения дерева использует документированное поведение [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Если политика ОС запрещает присоединение к Job Object, движок пишет диагностическое предупреждение; такая конфигурация здесь не проверена.

## Ограничения вывода

Исходный зависший экземпляр не был доступен. Тестовые экземпляры приложения запускались с отдельными профилями. Поэтому конкретный ежедневный эпизод со скриншота не установлен по журналу зависшего процесса. Воспроизведён реальный дефект Unicode-истории и проверены исправления механизмов, способных вызвать описанные симптомы; это не доказательство единственной причины всех прежних зависаний.

Суточный непрерывный прогон, разные версии GPU-драйверов, macOS/Linux и длительная нагрузка на резервный node-pty backend не проверены. Проверки UI выполнялись с отключённым GPU. Зависание внешнего агента, сети или системного вызова Windows не исключается исправлениями OrcSpace. В частности, создание нативного PTY остаётся синхронной операцией внутри командного цикла; отдельной проверки зависшего системного spawn здесь нет.

Автовосстановление относится к **падению** renderer, но не обнаруживает произвольный бесконечный цикл в ещё живом renderer. При падении самого движка работа AI-агента теряется: можно восстановить оболочку, но нельзя автоматически продолжить его прежнее внутреннее состояние.

При полном зависании потребителя вывода ACK всё равно не может физически вернуться, но команды больше не ждут записи в stdout. Очередь ответов ограничена 4096 пакетами: при исчерпании движок завершает работу с очисткой терминалов, вместо бесконечного зависания или роста памяти.

Собраны локальные `out/` и `native/target/release/orcspace.exe`. Установленный экземпляр приложения автоматически не обновлялся; исправления нужно запускать из новой сборки. Установщик не создавался.
